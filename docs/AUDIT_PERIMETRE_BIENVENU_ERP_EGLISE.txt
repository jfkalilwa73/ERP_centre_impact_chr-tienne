1. RÉSUMÉ EXÉCUTIF
================================================================================

État général
------------
Le périmètre « base de données » est structurellement prometteur : le schéma est
lisible, les entités métier sont correctement modélisées, les contraintes CHECK
et les clés étrangères sont nombreuses, les index sont ciblés et les triggers
sont documentés. Le travail de fond (Phase 0 + Sprint 1) est réel.

En revanche, l'état livré n'est PAS reconstructible ni cohérent de bout en bout :

  * le schéma de la base de développement a divergé du code (migration 000010
    modifiée après avoir été appliquée ; migration 000017 non appliquée) ;
  * la suppression annoncée de `membre.famille_impact_id` n'est faite qu'à
    moitié : la colonne est retirée du fichier de migration mais reste dans le
    modèle `Membre`, dans le seeder et dans trois services de l'API ;
  * `php artisan migrate:fresh --seed` est cassé sur une base neuve ;
  * l'étape « Familles des Disciples » du seeder est un no-op sur base neuve,
    faute de départements créés par les seeders ;
  * l'auteur des changements de statut n'est jamais enregistré (12/12 lignes
    d'historique ont `change_par = NULL`) ;
  * la règle métier « au moins 1 membre de chaque département actif » n'est pas
    garantie : elle repose sur un département déclaré librement, jamais recoupé
    avec `affecter_departement` ;
  * aucun test automatisé ne couvre les triggers, contraintes, vues, migrations
    ou seeders ; il n'existe aucune CI ;
  * la documentation Sprint 1 contredit le schéma et annonce des validations
    qui n'ont pas de preuve.

Principaux points forts
-----------------------
  * Modélisation relationnelle cohérente et normalisée (personne / membre /
    famille / famille d'impact / affectation / présence / historique).
  * Contraintes d'intégrité nombreuses : UNIQUE, CHECK, FK, index partiel
    unique `uq_affectation_membre_active`.
  * Triggers PostgreSQL pertinents et correctement séparés (BEFORE INSERT pour
    le numéro, AFTER UPDATE pour l'historique, BEFORE DELETE pour la protection,
    BEFORE UPDATE pour `date_modification`).
  * Modèles Eloquent alignés sur le schéma, avec casts explicites et UUID
    générés côté application (contourne le problème de récupération des UUID
    par défaut PostgreSQL).
  * Seeder Sprint 1 désormais enveloppé dans `DB::transaction`.
  * `tests/TestCase.php` protège la base de développement en forçant
    `erp_eglise_test`.

Principaux risques
------------------
  1. Reconstruction impossible : ni `migrate:fresh --seed`, ni `db:seed` sur la
     base existante, ni `migrate` seul ne produisent un état conforme.
  2. Régression fonctionnelle : après migration fraîche, `POST /api/v1/.../membre`
     et l'affectation à une famille d'impact échouent (colonne inexistante).
  3. Intégrité métier : la règle des Familles des Disciples est déclarative et
     contournable.
  4. Sécurité : l'application et les tests utilisent un rôle PostgreSQL
     SUPERUSER avec BYPASSRLS.
  5. Traçabilité : l'auteur des changements de statut est perdu.

Problèmes les plus urgents (P0)
-------------------------------
  * Aligner modèle `Membre` / seeder / services sur la suppression de
    `famille_impact_id` (ou revenir sur la suppression), et fournir une
    migration de convergence non destructive.
  * Rendre la migration 000017 réellement applicable (elle ne l'est pas sur la
    base de dev) et rétablir un chemin de reconstruction vert.
  * Créer les données de référence (site + départements) avant l'étape 8 du
    seeder.

Limites de l'audit
------------------
  * Aucune migration, aucun seeder, aucun test applicatif n'a été exécuté
    (interdiction explicite + risque d'altération). Les conclusions de
    reconstruction sont donc issues de l'analyse statique, du schéma réellement
    présent dans les bases `erp_eglise` et `erp_eglise_test`, et de requêtes SQL
    en lecture seule.
  * Le comportement exact de `migrate:fresh` vis-à-vis de la séquence autonome
    n'a pas été observé (déduit du comportement PostgreSQL).
  * Aucun accès à un environnement isolé de test n'a été utilisé.

4. ARCHITECTURE ET CONCEPTION DES DONNÉES
================================================================================

Points forts
------------
  * Séparation claire identité (`personne`) / appartenance ecclésiale
    (`membre`) / regroupement (`famille`, `relation_familiale`) / groupe
    communautaire (`famille_impact`, `affecter_famille_impact`) /
    présence (`presence_famille_impact`) / historisation.
  * Clés primaires UUID cohérentes (`gen_random_uuid()`), clés étrangères
    nommées, index sur les colonnes de jointure et de filtre.
  * Contrainte UNIQUE sur `membre.id_personne` (une personne = un membre max).
  * Index partiel unique `uq_affectation_membre_active` : un membre n'a qu'une
    affectation active — correctement défini et effectivement présent en base.
  * CHECK sur `statut_membre`, `type_relation`, `nouveau_statut`, `sexe`,
    `statut` de `personne`.
  * Triggers PostgreSQL isolés dans des fonctions nommées, avec messages
    d'erreur explicites.

Incohérences et défauts confirmés
---------------------------------
  1. Triple source de vérité pour l'appartenance à une famille d'impact :
     `membre.famille_impact_id` (héritage Phase 0), `appartenir_famille`
     (Phase 0, encore utilisé par l'API) et `affecter_famille_impact`
     (Sprint 1). La suppression de `membre.famille_impact_id` est annoncée mais
     non appliquée en base, et le code continue de l'utiliser.
  2. `famille_disciple` / `composition_famille_disciple` ne portent aucune
     contrainte de cohérence temporelle (`periode_fin >= periode_debut`,
     `date_fin >= date_debut`).
  3. `composition_famille_disciple.departement_origine_id` est une déclaration
     libre : rien ne garantit que le membre est réellement affecté à ce
     département (`affecter_departement` n'est jamais consulté).
  4. `famille_disciple.responsable_id` n'est pas obligatoire et n'est pas
     contraint à appartenir à la composition du groupe.
  5. `presence_famille_impact` n'a aucune unicité sur
     (`id_affectation`, `date_reunion`) : doublons possibles et observés.
  6. `relation_familiale` n'interdit pas l'auto-relation, les doublons ni les
     incohérences de dates.
  7. `personne` ne possède pas de colonne email ; le dédoublonnage annoncé
     (nom, téléphone, email) n'est pas outillé.
  8. `membre` conserve un index `idx_membre_personne` redondant avec la
     contrainte UNIQUE (`membre_id_personne_key`).

Risques
-------
  * Corruption logique par déclaration d'un département non réel.
  * Historique de composition perdu en cas de suppression d'un groupe
    (`ON DELETE CASCADE`).
  * Perte de traçabilité de l'affectation famille d'impact (deux tables
    alimentées de façon partiellement indépendante).
  * Croissance non maîtrisée des doublons de présence.

Améliorations recommandées
--------------------------
  * Choisir UNE source de vérité pour l'appartenance famille d'impact et
    supprimer/archiver les deux autres (avec migration de convergence).
  * Ajouter les CHECK temporels et un index partiel d'unicité sur les
    compositions actives.
  * Vérifier le département via `affecter_departement` (contrainte applicative
    ou vue corrigée).
  * Ajouter UNIQUE (`id_affectation`, `date_reunion`) sur les présences.
  * Documenter et appliquer une politique de suppression unique (RESTRICT
    partout ou CASCADE justifié).

5. AUDIT DES MIGRATIONS
================================================================================

Résultats détaillés
-------------------
  * 18 migrations sont présentes dans backend/database/migrations.
  * 17 sont enregistrées dans la base `erp_eglise` (batch 1).
  * 18 sont enregistrées dans la base `erp_eglise_test`.

Dépendances et ordre d'exécution
--------------------------------
  * 000010 (table `membre`) crée un trigger `trg_historique_statut_membre` qui
    insère dans `historique_statut_membre`, table créée seulement par 000015.
    La création du trigger réussit, mais toute mise à jour de `membre` entre
    000010 et 000015 échouerait. CONFIRMÉ par lecture, NON REPRODUIT.
  * 000010 crée la séquence `seq_numero_membre_2026` ; cette séquence n'est ni
    possédée par la table ni supprimée par `down()`.

Cohérence du schéma et reproductibilité
---------------------------------------
  * PROBLÈME MAJEUR : la migration 000010 a été modifiée APRÈS son application.
    Preuve dans la base `erp_eglise` :
      - `membre.famille_impact_id` existe encore ;
      - `idx_membre_famille_impact` existe encore ;
      - la séquence `seq_numero_membre_2026` est ABSENTE de `pg_sequences` ;
      - `pg_proc.generer_numero_membre` contient encore `SELECT COUNT(*) FROM
        membre`, et non `NEXTVAL`.
    Conséquence : `php artisan migrate` ne rejouera pas 000010 ; la base de
    développement restera dans un état hybride.
  * PROBLÈME MAJEUR : la migration 000017 n'est PAS appliquée dans `erp_eglise`
    (`to_regclass('public.famille_disciple')` = NULL,
    `composition_famille_disciple` = NULL, vue = NULL), alors qu'elle EST
    appliquée dans `erp_eglise_test`. Le code des nouveaux modèles échouera donc
    sur l'environnement de développement courant.
  * La base `erp_eglise_test` a bien le schéma cible (colonne `famille_impact_id`
    absente, tables et vue présentes), ce qui prouve que le fichier de migration
    produit le bon schéma sur une base neuve — mais aussi que la base de dev est
    en dérive.

Risques de perte de données
---------------------------
  * `migrate:fresh` est la seule voie pour aligner une base neuve sur le fichier
    000010 ; elle détruit toutes les données.
  * `down()` de 000010 ne supprime pas la séquence : résidu après rollback.
  * `down()` de 000017 supprime la vue puis les tables : ordre correct, mais la
    perte des compositions est définitive.

Problèmes de compatibilité
--------------------------
  * `DB::unprepared` avec SQL brut est cohérent avec le style Phase 0, mais
    interdit le `--pretend` fiable et rend le rollback partiel fragile.
  * `gen_random_uuid()` est natif en PostgreSQL 16 (aucune extension requise) :
    ce point est correct malgré l'absence de `pgcrypto`.

7. AUDIT DES SEEDERS ET DES DONNÉES
================================================================================

Ordre d'exécution
-----------------
  `DatabaseSeeder` appelle `Phase0ScenarioSeeder` puis
  `Sprint1MembresFamillesSeeder`.

Cohérence avec les migrations et intégrité référentielle
--------------------------------------------------------
  * CORRECT : le seeder Sprint 1 génère explicitement les UUID et les passe aux
    modèles (`id_famille`, `id_membre`, `id_affectation`, etc.), ce qui évite le
    défaut Eloquent/PostgreSQL sur les UUID par défaut.
  * CORRECT : le seeder est enveloppé dans `DB::transaction(...)`, donc un échec
    annule les écritures du Sprint 1.
  * INCORRECT : `Membre::create([... 'famille_impact_id' => null])` (ligne 124)
    alimente une colonne absente du schéma cible. Vérifié par exécution PHP :
    le mass assignment conserve bien l'attribut `famille_impact_id`, donc
    l'INSERT l'inclut.
  * INCORRECT : l'étape 8 dépend de `departement`, mais AUCUN seeder ne crée de
    site ni de département. Preuve : `Phase0ScenarioSeeder` ne contient aucun
    appel à `Site::` ou `Departement::` ; il ne crée que l'utilisateur, le rôle
    et les permissions. Sur base neuve, `$departementsActifs` est vide et
    l'étape 8 est silencieusement ignorée.
  * INCORRECT : `change_par` est passé à `Membre::update()` (ligne 454) alors
    que `change_par` n'est pas une colonne de `membre` et n'est pas dans
    `$fillable`. Eloquent l'ignore silencieusement. Preuve en base :
    12/12 lignes de `historique_statut_membre` ont `change_par IS NULL`.

Validité des données générées (base `erp_eglise`)
-------------------------------------------------
  * Volumétrie réelle observée : 65 membres, 25 familles, 72 relations
    familiales, 6 familles d'impact, 46 affectations, 251 présences,
    12 historiques, 1 département, 1 site.
  * 3 membres ont une `date_integration` FUTURE (maximum observé :
    2026-12-26) à cause du tirage aléatoire 2020-2026.
  * 14 membres au statut `inactif` ou `archive` possèdent encore une affectation
    famille d'impact active.
  * 2 doublons de présence observés (même `id_affectation`, même
    `date_reunion`).
  * 67 personnes pour 65 membres : les 2 personnes excédentaires proviennent de
    l'environnement (utilisateur/compte), pas du seeder Sprint 1.

Reproductibilité et idempotence
-------------------------------
  * Le seeder est aléatoire (`array_rand`, `rand`) sans seed Faker : deux
    exécutions produisent des données différentes.
  * Le seeder n'est pas idempotent : une seconde exécution viole
    `famille_impact.code` / `famille_impact.nom` (UNIQUE) et échoue, avec
    rollback de l'ensemble.
  * Sur la base existante, `db:seed` échoue donc à l'étape 4 (codes déjà
    présents) même si l'étape 1 passe (colonne encore présente).

Dépendances entre seeders
-------------------------
  * Sprint 1 dépend de `User::first()` (fallback) : tolérant.
  * Sprint 1 dépend de `departement` pour l'étape 8 : dépendance non satisfaite
    par les seeders. C'est la cause directe du no-op.

Risques
-------
  * Données de test non conformes aux règles métier (dates futures, archives
    avec affectation active).
  * Impossibilité de reconstruire un jeu de données de référence stable.
  * Confiance excessive dans des volumétries non reproductibles.

8. AUDIT DES TRIGGERS, FONCTIONS ET VUES
================================================================================

Inventaire (base `erp_eglise`)
------------------------------
  Fonctions :
    update_date_modification()            (Phase 0)
    prevent_active_personne_delete()      (Phase 0)
    generer_numero_membre()               (Sprint 1 — version COUNT(*))
    enregistrer_historique_statut_membre()(Sprint 1)
    prevent_active_membre_delete()        (Sprint 1)
  Triggers sur `membre` :
    trg_numero_membre_auto        BEFORE INSERT
    trg_historique_statut_membre  AFTER UPDATE
    trg_prevent_active_membre_delete BEFORE DELETE
    trg_membre_modification       BEFORE UPDATE
  Triggers sur `personne` :
    trg_personne_modification, trg_prevent_active_personne_delete

Rôle de chaque objet
--------------------
  * `generer_numero_membre` : génère `MEM-<année>-<séquence>` si le numéro est
    vide. Version livrée en base : `COUNT(*) + 1` (fragile). Version du fichier :
    `NEXTVAL('seq_numero_membre_2026')` (plus robuste).
  * `enregistrer_historique_statut_membre` : insère une ligne à chaque
    changement de statut, avec `change_par = NULL` codé en dur.
  * `prevent_active_membre_delete` : interdit la suppression d'un membre actif.
  * `trg_membre_modification` : met à jour `date_modification`.
  * Vue `vue_completude_famille_disciple` : présente uniquement dans
    `erp_eglise_test` ; exécution réussie, 5 colonnes, 0 ligne.

Vérifications effectuées
------------------------
  * Lecture de `pg_proc.prosrc` : la base de dev utilise encore `COUNT(*)`.
  * Lecture de `pg_sequences` : `seq_numero_membre_2026` absente.
  * Lecture de `pg_trigger` / `\d membre` : 4 triggers présents.
  * Exécution `SELECT * FROM vue_completude_famille_disciple` sur
    `erp_eglise_test` : succès, colonnes conformes.

Défauts observés
----------------
  * Le générateur `COUNT(*)` est incorrect après suppression : si un membre non
    actif est supprimé, le compteur diminue et le prochain numéro réutilise une
    valeur déjà attribuée -> violation UNIQUE. Confirmé par analyse.
  * Le trigger d'historique ne peut pas connaître l'auteur (NULL en dur) ; la
    correction applicative est faite a posteriori par `MembreService`
    (UPDATE de la dernière ligne), ce qui est fragile.
  * La vue ne vérifie pas l'appartenance réelle du membre au département.
  * La vue ne filtre ni le statut du membre, ni `date_fin IS NULL` ; seule la
    colonne `actif` de la composition est filtrée.
  * Si aucun département n'est actif, la condition `>= 0` rend toutes les
    familles « COMPLET » (vérité vacuelle).
  * Alias accentué `nb_departements_représentes` : valide en PostgreSQL 16 mais
    dépendant de l'encodage client et mal orthographié.

Scénarios non vérifiés
----------------------
  * Comportement sous concurrence de deux INSERT simultanés (séquence vs COUNT).
  * Rollback partiel d'une transaction contenant un changement de statut.
  * Comportement de la vue après suppression d'un département (RESTRICT).
  * Comportement du trigger de suppression combiné aux FK RESTRICT.

9. AUDIT DE SÉCURITÉ ET D'INTÉGRITÉ
================================================================================

Risques de sécurité
-------------------
  * Le rôle PostgreSQL `erp_user` est SUPERUSER, CREATEDB, CREATEROLE et
    BYPASSRLS. Preuve : `SELECT rolname, rolsuper, ... FROM pg_roles`.
    Impact : toute injection SQL ou compromission applicative donne le contrôle
    total du cluster et de toutes les bases (dont `erp_eglise_test`).
  * Identifiants de développement en clair dans des fichiers versionnés :
      - docker-compose.yml (utilisateur/mot de passe PostgreSQL, Redis,
        MinIO, pgAdmin) ;
      - backend/phpunit.xml (utilisateur/mot de passe PostgreSQL) ;
      - backend/tests/TestCase.php (mêmes identifiants en dur) ;
      - backend/.env.example (valeurs par défaut) ;
      - README.md (identifiants pgAdmin).
    Les valeurs ne sont pas reproduites ici. Rotation et externalisation
    recommandées.
  * `backend/.env` n'est pas suivi (couvert par .gitignore) : point positif.
  * `frontend/.env` est suivi : pas de secret observé, mais l'habitude est
    risquée.
  * `phpunit.xml` et `TestCase.php` forcent `DB_HOST=postgres` : les tests ne
    peuvent pas tourner hors Docker et la configuration est dupliquée.

Protection des données
----------------------
  * Les données personnelles (nom, prénom, date de naissance, téléphone,
    adresse) sont stockées sans chiffrement applicatif : acceptable pour un ERP
    interne, à documenter.
  * Aucune policy RLS, aucune séparation de rôles en lecture/écriture.
  * UUID exposés dans les URLs (l'API utilise `/membres/{uuid}`) : risque
    d'énumération faible mais réel, déjà signalé dans la documentation.

Intégrité relationnelle
-----------------------
  * FK nombreuses et correctement orientées.
  * `affecter_famille_impact.id_famille_impact` est NOT NULL : correct.
  * `composition_famille_disciple` utilise CASCADE sur `membre` et sur
    `famille_disciple`, mais RESTRICT sur `departement` : politique hybride.
  * `historique_statut_membre` est mutable (aucun trigger d'immuabilité) ;
    l'API modifie la ligne pour renseigner `change_par`.

Historisation
-------------
  * Le statut est historisé automatiquement : point fort.
  * L'auteur n'est pas historisé par le trigger (NULL), et l'API corrige la
    dernière ligne : perte possible en cas de concurrence.
  * Les affectations et compositions ne sont pas historisées par trigger ;
    seule la table elle-même conserve `date_debut`/`date_fin`/`actif`.
  * `audit_log` existe mais aucun trigger ne l'alimente : la traçabilité
    « automatique » annoncée n'est pas démontrée.

Gestion des erreurs
-------------------
  * `MembreService::creer` attrape toute `QueryException` et renvoie 409
    « déjà membre » : cela masque les erreurs SQL réelles (dont l'erreur
    `undefined column`), ce qui rend le diagnostic difficile — et transforme la
    régression actuelle en faux conflit métier.

17. VERDICT FINAL
================================================================================
Le périmètre Bienvenu n'est PAS livrable en l'état.

Ce qui peut être considéré comme fiable :
  * la conception relationnelle et la nomenclature ;
  * les contraintes d'intégrité et les index déjà en place ;
  * la logique des triggers (numéro, historique, protection, date de
    modification) ;
  * les modèles `FamilleImpact`, `FamilleDisciple`,
    `CompositionFamilleDisciple` ;
  * la migration 000017 sur une base neuve (schéma et vue valides, vérifiés en
    base de test).

Ce qui reste incertain :
  * le comportement exact de `migrate:fresh` vis-à-vis de la séquence autonome ;
  * le comportement concurrent du générateur de numéro et de l'historisation ;
  * la portée réelle des données de la base de dev (créées hors seeder) ;
  * l'impact complet sur l'API, faute d'exécution de la suite de tests.

Ce qui nécessite une intervention :
  * la suppression inachevée de `membre.famille_impact_id` (bloquant) ;
  * la dérive de schéma entre le fichier 000010 et la base de dev (bloquant) ;
  * l'absence de départements dans les seeders (bloquant pour l'étape 8) ;
  * l'absence de tests DB et de CI (risque structurel) ;
  * la documentation non conforme (risque de contrat) ;
  * le rôle PostgreSQL superuser et les secrets versionnés (risque sécurité).

Conclusion : les fondations sont bonnes, mais la livraison est incomplète et
non reconstructible. Un effort ciblé P0 (alignement du modèle, migration de
convergence, référentiel site/départements, reconstruction verte) est
indispensable avant de déclarer le Sprint 1 opérationnel ou de poursuivre sur
le Sprint 2.
